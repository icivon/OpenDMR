# M17 数字格式收发评估

本文评估在 OpenDMR 固件中增加 M17 数字语音收发的可行性、软件来源、开发工作量、测试方案和实施建议。结论：技术上可行，但属于较大且需射频实测的新模式，应分阶段实施。

## 1. 当前项目基础

OpenDMR 当前基于：

- 目标硬件：Baofeng DM-32UV，HR_C7000 / DH4570 SoC，CK803S 168 MHz；
- 实时系统：FreeRTOS；
- 数字模式：DMR、P25 Phase 1、NXDN48；
- 模拟模式：FM、AM、USB、LSB；
- 射频和基带：FD6818 完成射频前端，HR_C7000 完成数字调制解调和音频接口；
- 声码器：DMR AMBE+2、P25 IMBE 已进入互斥 overlay RAM 区；
- 现有架构已经支持数字模式独立于 DMR 引擎运行。

尤其是 P25 和 NXDN 的实现证明了以下可复用能力：

- 在数字信道下绕过 DMR 帧引擎，直接使用 HR_C7000 的物理层判决或 FD6818 鉴频音频；
- 中断只搬运数据，协议解码放到 FreeRTOS 任务中；
- 使用环形 FIFO 缓冲接收块和 PCM；
- 独立完成帧同步、纠错、声码器解码和发射状态机；
- 在收发时动态切换射频频率、PA/LNA、话筒路由和音频输出；
- 使用 RAM overlay 装载多个声码器，不与主固件常驻代码冲突。

相关代码参考：

- `src/services/radio.c`
- `src/services/p25_radio.c`
- `src/services/p25_phy.c`
- `src/services/nxdn_radio.c`
- `src/services/nxdn_core.c`
- `src/dmr/dmr_sound.c`
- `src/dmr/dmr.c`
- `src/drivers/fd6818.c`
- `src/ckcpu.ld`

## 2. M17 通讯标准

M17 是面向业余无线电的开放数字语音协议，主要特性包括：

- 调制：4FSK；
- 符号率：4800 symbols/s；
- 每符号：2 bit；
- 空中位速率：约 9600 bit/s；
- 目标信道带宽：12.5 kHz；
- 常用语音编码：Codec2 3200 bps；
- 链路类型：Stream、Packet、Link Setup 和 EOT/Termination；
- 呼号：采用 M17 的呼号编码方式；
- 纠错：卷积码、Viterbi、Golay、CRC 等；
- 常见帧：预导、Link Setup Frame、Stream Frame、Packet Frame 和结束帧；
- 网络生态：Reflector、MMDVM、第三方客户端和热点。

协议实现应以 `M17-Project/M17_spec` 和官方开源实现为准，不应只依据某一次抓包或单一软件推断帧格式。

规范和实现：

- 规范：<https://github.com/M17-Project/M17_spec>
- 官方库：<https://github.com/M17-Project/libm17>
- 实现集合：<https://github.com/M17-Project/M17_Implementations>
- GNU Radio：<https://github.com/M17-Project/gr-m17>
- Python：<https://github.com/M17-Project/pyM17>
- 工具集：<https://github.com/M17-Project/m17-tools>

## 3. 软件可移植项目

### 3.1 Codec2

项目：<https://github.com/drowe67/codec2>

用途：

- M17 常用的 Codec2 3200 编解码；
- 16 kHz 对 8 kHz 音频需要另行确认采样和环形缓冲；
- 可作为语音编码的首要参考和移植来源。

需要特别注意：

- Codec2 包含浮点算法，CK803S 没有浮点硬件；
- 官方文档要求微控制器移植时切换嵌入式模式并优化浮点/内存；
- 不应直接编入全部 FreeDV、OFDM、700C 等无关模式；
- 首期只编译 Codec2 3200 及其编码、解码和必要的 FFT/量化表；
- LGPL-2.1 许可和本项目商业限制需要独立评估。

当前项目已有的结构可以复用：

- 麦克风采集和 PCM 放音环：`src/dmr/dmr_sound.c`；
- 声码器 RAM overlay：`src/ckcpu.ld`；
- 编码器放 RAM、解码器放 Flash 的分区经验；
- 调试版的编码耗时和栈使用统计。

### 3.2 libm17

项目：<https://github.com/M17-Project/libm17>

这是协议层优先考虑的基础库：

- C 实现；
- 专注帧编解码；
- 包含呼号编码、LICH、Golay、卷积码和 CRC 的基础；
- 可以拆成独立的嵌入式模块；
- 比完整固件更容易移植到 CK803S。

移植时应去除依赖主机动态分配、大块栈和浮点运算的部分，再集成到固件自己的任务和 FIFO 中。

### 3.3 OpenRTX

项目：<https://github.com/OpenRTX/OpenRTX>

OpenRTX 的 M17 实现具有很高的参考价值：

- 完整 4FSK 调制和解调；
- RRC 基带滤波；
- 时钟恢复；
- Link Setup、Stream、Packet 和 EOT；
- Codec2 集成；
- 基带录波回放工具；
- 噪声和已知帧单元测试。

可重点参考：

- `openrtx/src/protocols/M17/Demodulator.cpp`
- `openrtx/src/protocols/M17/Modulator.cpp`
- `openrtx/src/protocols/M17/FrameEncoder.cpp`
- `openrtx/src/protocols/M17/FrameDecoder.cpp`
- `openrtx/include/protocols/M17/`
- `tests/platform/M17Replay.*`
- `tests/platform/M17Signal.*`

不建议整体移植：

- 主要是 C++；
- 依赖 OpenRTX 平台抽象、RTOS 和音频路径；
- 调制器和解调器仍有浮点部分；
- 许可证为 GPL-3.0，与本项目非商业许可不能直接混合。

可采用“参考协议与测试，重写为 C”而不是直接合并源码的策略。

### 3.4 GNU Radio 和 m17-tools

用途：

- Linux 和 SDR 环境中的协议实现；
- 信号回放和录制；
- 已知数据帧生成；
- 异常帧、噪声、频偏和符号误码测试；
- 与实际射频设备交叉验证。

它们适合开发主机端参考程序，不适合直接运行在 CK803S 上。

### 3.5 MMDVM 和 M17Gateway

项目：

- <https://github.com/M17-Project/MMDVM_HS>
- <https://github.com/M17-Project/M17Gateway>

用途：

- 网络和热点互通；
- MMDVM 串行帧接口参考；
- M17 Reflector 接入参考；
- 第二阶段或网络互通阶段测试。

射频协议核心和热点网络协议可以分离：第一阶段只做射频收发，后续再接入 MMDVM 和 Reflector。

## 4. 建议架构

建议增加独立模块：

```text
src/m17/
    m17_radio.c/h       模式切换、PTT、链路状态
    m17_phy.c/h         4FSK 接收和发射、符号同步
    m17_frames.c/h      LSF、Stream、Packet、EOT
    m17_codec2.c/h      Codec2 编解码封装
    m17_callsign.c/h    呼号编码和解码
```

与现有链路的集成点：

1. `codeplug.h` 增加 `CODEPLUG_MODE_M17`；
2. `codeplug.c` 增加模式顺序、名称和存储标记；
3. `radio.c` 增加 M17 信道启动、停止、接收和 PTT 分支；
4. `dmr.c` 或独立 ISR 分支中读取判决块并通知 M17 任务；
5. `dmr_sound.c` 复用或拆分出通用 PCM 接收环；
6. `tx_target.c` 增加呼号、目标模块和呼叫类型；
7. `channel_screen.c`、`vfo_screen.c`、`tx_screen.c` 增加 M17 显示；
8. `scan.c` 增加 M17 同步帧或 LSF 被解出的判断；
9. `ckcpu.ld` 增加 Codec2 或新增 M17 独立 overlay；
10. Makefile 增加协议核心、Codec2 源码和测试宏。

中断中只进行最短操作：读取判决值、存入环形缓冲、通知任务。所有 Viterbi、Golay、帧解码、呼号解码和 PCM 解码都放在任务中。

## 5. 软硬件关键风险

### 5.1 HR_C7000 调制兼容性

HR_C7000 已能切换到数字物理层模式并处理 P25 4FSK。仍需验证：

- 4800 symbols/s 是否能稳定输出和接收；
- 频偏容差；
- 四电平间距和判决门限；
- 方波、滤波和抽样时钟是否和 M17 波形兼容；
- 发射频率校准是否足够精确；
- M17 的 RRC 滤波是否需要在基带软件实现。

### 5.2 CK803S 实时性

CPU 无浮点硬件，需预先测量：

- Codec2 3200 编码耗时；
- Codec2 3200 解码耗时；
- Viterbi 解码耗时；
- 4FSK 相关匹配和时钟恢复耗时；
- 20 ms 音频缓冲和 FreeRTOS 切换开销；
- 中断占用和播放环 underrun；
- 任务栈和 overlay RAM 高水位。

### 5.3 RAM 布局

现有声码器/升级区域约 74.8 KB，其中：

- DMR AMBE overlay；
- P25 IMBE overlay；
- 升级程序复用区。

M17 的 Codec2 可能无法与 AMBE 或 IMBE 同时常驻，需放置第三个互斥 overlay，或者重新评估总覆盖区布局。

## 6. 开发工作量

基于熟悉当前固件且具备射频实测能力的评估：

| 工作项 | 预计人周 |
|---|---:|
| M17 帧格式、呼号、CRC、Golay、Viterbi | 3–5 |
| Codec2 3200 移植和固定量化优化 | 2–4 |
| 4FSK 解调、符号同步和频偏容忍度 | 2–4 |
| 发射帧、预导、时序和 PTT 状态机 | 1–2 |
| 模式切换、任务、FIFO 和 RAM overlay 集成 | 2–3 |
| UI、信道、VFO、扫描和呼号显示 | 1–2 |
| CPS 和码表格式兼容 | 1–3 |
| 二机互通、热点、弱信号和回归测试 | 3–6 |

合计：

- 最低可用协议和发射验证：**8–12 人周**；
- 稳定语音收发：**12–18 人周**；
- 中继、热点、Packet 和完整生态兼容：**18–26 人周**。

具体范围取决于：

- 是否要求直接支持 Codec2 3200 语音编码；
- 是否要求商用级弱信号性能；
- 是否先做接收还是同时做收发；
- 是否接入 MMDVM 和 Reflector；
- CPS 是否需要原生 M17 信道格式；
- 是否需要加密、Packet、GPS 和元数据。

## 7. 没有 M17 对讲机时的测试方案

### 阶段 A：纯软件和已知向量

不需要射频硬件：

- 使用 OpenRTX 的已知帧和 `M17Signal` 测试信号；
- 使用 `m17-tools` 和 GNU Radio 生成标准符号；
- 测试 CRC、呼号、Viterbi、LICH、Stream 和 Packet；
- 保存编码后的帧和符号逐位比对；
- 长时间运行检查任务死锁、缓冲溢出和内存覆盖；
- 在 PC 上交叉运行两套独立实现。

### 阶段 B：基带录音和回放

使用声卡、SDR 或普通 9600 bps 基带接口：

- PC 生成标准 M17 RRC 基带或符号流；
- 固件解码并保存接收状态；
- 固件生成已知帧并由另一套软件解码；
- 测量符号时钟、频偏、四电平、相位反转和噪声容限；
- 检查 Codec2 音频、丢帧和播放环抖动；
- 录制和回放统一用已知的原始 PCM 格式。

OpenRTX 的 `M17Replay` 和录波工具适合形成第一批主机端回放测试。

### 阶段 C：无天线射频闭环

准备：

- 衰减器；
- 屏蔽盒或无天线测试条件；
- SDR 接收机或另一套解调软件；
- 标准软件或热点作为参考发射源；
- 足够低的许可频段发射功率。

测试路径：

```text
固件发射 -> 衰减器 -> SDR -> 软件解码
```

以及：

```text
标准软件发射 -> 衰减器 -> 固件射频输入 -> 固件解码
```

不要直接带天线进行未知频偏下的射频测试。开始时只发已知静音帧、单一呼号和固定序列。

### 阶段 D：MMDVM/Reflector 互通

使用虚拟客户端或现有网络设备：

```text
固件射频 -> MMDVM 热点 -> M17 Reflector -> 第三方客户端
```

反向同样可测试。重点验证：

- Link Setup 呼号和目标；
- Stream 序号；
- EOF 和超时；
- 丢帧和重新锁定；
- 模块名和私呼/组呼；
- MMDVM 串行接口和重复帧；
- Reflector 的传输延迟和结束帧。

## 8. 实施里程碑

### 里程碑 1：协议离线验证

目标：

- 编解码已知帧；
- 呼号编解码；
- CRC、LICH、Viterbi 验证；
- 通过已知流量和已知错误帧测试。

预计：**2–4 人周**。

### 里程碑 2：Codec2 与基带验证

目标：

- Codec2 3200 编解码通过性能基准；
- 固件通过录波解码标准 M17；
- 固件输出的帧能被 GNU Radio 或 OpenRTX 解码。

预计：**再增加 3–5 人周**。

### 里程碑 3：射频收发

目标：

- 在 HR_C7000 上完成 4FSK 接收和发射；
- 与 SDR 或标准软件射频互通；
- 完成 PTT、超时、结束帧和呼叫显示。

预计：**再增加 4–7 人周**。

### 里程碑 4：网络和成熟度

目标：

- MMDVM 热点或 Reflector 互通；
- 弱信号和频偏测试；
- 多小时稳定性；
- CPS 和用户界面完善。

预计：**再增加 4–8 人周**。

## 9. 建议结论

- **可行性：高**。现有 P25/NXDN 物理层和任务架构已具备数字格式集成基础。
- **主要难点：** Codec2 在 CK803S 上的实时性、HR_C7000 的 M17 4FSK 精度、解调时钟恢复和 RAM overlay。
- **优先来源：** `libm17` 做协议核心，Codec2 官方库做语音编解码，OpenRTX 做调制解调参考和测试向量。
- **实现原则：** 不整库移植、不依赖动态分配、不使用浮点 M17 主循环，以整数 C 和现有事件驱动任务为主。
- **首轮目标：** 离线帧 + 基带录放 + 已知射频闭环，而不是一开始就做完整网络和 CPS。
- **推荐投入：** 初版至少 8–12 人周；稳定收发建议按 12–18 人周规划。

正式开发前应先用一周左右完成两个基准：

1. Codec2 3200 编码/解码和 RAM 占用；
2. HR_C7000 的 M17 4800 symbols/s 接收、判决和发射符号输出。

两个基准通过后，再开始全量协议集成。

## 10. 许可证检查清单

移植每个模块前必须单独确认许可证：

- Codec2：LGPL-2.1；
- OpenRTX：GPL-3.0；
- `libm17` 和各官方工具：逐仓库确认；
- 本项目：已有商业使用限制；
- 若商业化：不能直接合并 GPL 模块或其衍生代码；
- 所有移植文件保留作者、许可证和来源声明；
- 标准协议的数据格式和算法本身不等同于任何实现都可直接商用，需要逐项审查源码许可。
